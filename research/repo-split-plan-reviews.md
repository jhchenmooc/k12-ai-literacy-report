# repo 拆分搬遷方案：模型模擬審查紀錄

> 對應 [repo-split-plan.md](repo-split-plan.md)。各表的「處理」欄為當時版本的做法；現行做法以方案本文為準。**所有審查都是 Anthropic 模型的角色模擬，不是外部真人審查。**

## 第一輪：Sonnet（v0.1 → v0.2）

管理者要求三輪不同模型審查。本輪四個角度皆由 Sonnet 執行，各自獨立閱讀 v0.1，共 37 項意見。

**GitHub 平臺審查者對照官方文件確認的事項**：

- 免費方案的 Pages 只能用在公開 repo；
- 改成私人後，Pages 自動取消發佈，star 與 watcher 清除；
- 私人 repo 的 Issue 不能轉到公開 repo；
- 免費方案的私人 repo，Actions 每月 2,000 分鐘；
- 用 `GITHUB_TOKEN` 推送不會觸發分支部署的 Pages 建置。

**修正者另行抽查屬實的事項**：

- 兩個測試寫死舊 repo 網址；
- 讀者回饋整理程式依 `GITHUB_REPOSITORY` 讀取 Issues；
- 另有 7 個頁面含舊 repo 網址。

| 角度 | 意見數 | 主要發現 | 處理 |
|---|---|---|---|
| GitHub 平臺與資安 | 10 | 個人帳號無法限制只有部署機器人推送；建議部署金鑰而非個人權杖；只比對檔名不夠，要掃內容；commit 訊息不放私人 SHA；workflow 觸發與注入；缺誤推處置；`GITHUB_TOKEN` 推送不會觸發 Pages；Actions 額度可具體化；改私人的其他效應；轉址替代做法 | 改寫保護方式，重點放在私人端三道檢查；改用部署金鑰；加內容掃描；commit 訊息改為期別；規定觸發與寫法；加誤推處置；註明必須用金鑰；寫入 2,000 分鐘；補效應；轉址列為 S8 |
| CI 與專案流程 | 8 | 兩個測試寫死舊網址；首頁、about、archive 是程式產生的，直接改 HTML 會被覆蓋；讀者回饋檔案與「推送清單等於網站清單」衝突；步驟順序三處漏洞；舊刊連結可依 legacy 規則修；知識庫連結會 404；SOP 要改的地方列得太籠統；部署 job 權限與變數 | 網址常數加改測試；改產生程式再重新產生；公開清單納入 `.github/` 例外；觸發先手動、表單在步驟 4 測；舊刊文件放進 `methods/`；知識庫公開；列出具體檔案；補權限與 concurrency |
| 透明度與讀者 | 10 | 已刊主張的查核資料必須公開，不能列為待定；快照範圍；缺更正紀錄與部署證據；揭露不足；舊刊不要留下壞連結；方法 SOP 與知識庫不該待定；讀者回饋連續性；缺完整性保證；私人類別要說明理由；已公開歷史 | 新增第 2 節原則；公開 `verification/`、`corrections/`、`methods/`、`knowledge-base/`；部署清單附雜湊；about 頁新增透明度一節；舊 Issue 匯出歸檔 |
| 執行風險與回復 | 9 | 改私人不可回復卻寫成可回復；切換期沒定義正本；在途 PR、排程、session 未處理；推送失敗沒有監測；缺切換清單；管理者時間與時程；應正式比較「只搬草稿」的替代方案；額度與舊 Issue；舊網址 | 改為「實質不可回復」並訂回復程序；兩站並行、舊站為正本；加凍結窗口；冒煙測試；加第 7.1 節清單；管理者兩個時段、11/9 以後；新增 S0 方案比較 |

**未採納或部分採納**：

| 建議 | 決定 | 理由 |
|---|---|---|
| 快照附 Internet Archive 存檔連結，讀者可申請查驗原件（透明度） | 部分採納：沿用現行短快照與 SHA-256，原件申請管道另案 | 先不增加新工作流程 |
| 重大版本加簽署標籤或 GitHub Release（透明度） | 不採納 | 低人力；以部署清單附雜湊代替 |
| 建議乙方案或「先乙後甲」（執行風險） | 列為 S0，建議甲 | 乙的 CI 跨 repo 問題較難；由管理者決定 |

## 第二輪：Fable（v0.2 → v0.3）

本輪四個角度皆由 Fable 執行，各自獨立閱讀 v0.2，共 36 項意見。

**GitHub 平臺審查者對照官方文件確認的事項**：

- 部署金鑰推送會觸發分支部署的 Pages；
- Pages 站台上限 1 GB、每小時 10 次建置都是軟限制，本專案遠低於上限；
- 免費方案的公開 repo 可用 ruleset，包括「限制檔案路徑」；
- 私人改回公開時，Actions 紀錄會公開；
- 公開 repo 60 天無活動，排程會被自動停用。

**修正者另行抽查屬實的事項**：

- `publication/sources/` 17 個快照中，有 8 個屬未刊的 10 月月報；
- `render-site.js` 第 182 行隱藏審查中候選。

| 角度 | 意見數 | 主要發現 | 處理 |
|---|---|---|---|
| 執行風險與回復 | 9 | 0 則日讓「連續 7 次」失效；推送放在同一 workflow 會干擾舊站結果；預覽與雜湊一致互斥；凍結窗口與每日短訊衝突、權限試跑太晚；時程擠在 10/30–11/1；冒煙測試會被舊內容騙過；回復不必改回公開；PR 太大；分支與本方案已公開 | 空差異算成功，改為 7 天無失敗加 3 天有變更；獨立 workflow 與開關；`SITE_MODE`；切換日暫停短訊一次、權限試跑提前到步驟 3；前 3 個 PR 提前；`deploy.json` 輪詢；三級回復；拆成 PR-A 至 PR-F；補分支清單 |
| 透明度與讀者 | 9 | 兩本舊刊的查核紀錄沒列入；不做轉址犧牲讀者；知識庫 873 筆未核紀錄與私人路徑；`methods/` 兩個版本做不到；「無法公開就標示」沒有機制；讀者回饋歸檔資訊太少；「不是第三方稽核」讀者看不懂；預覽讓讀者困惑；整體太重 | 加 `verification/legacy/`；轉址維持選項，但加 canonical 作最低成本替代；知識庫加說明並改寫路徑；`methods/` 原樣公開；改為「先建機制再刊出」；歸檔加去識別化摘要；寫進「我們不宣稱的事」並說明能核對什麼；改寫預覽橫幅；不再人工逐站確認 |
| GitHub 平臺與資安 | 9 | 掃描詞會誤擋又掃不到真正的風險；金鑰使用方式未定義，可能印進紀錄；低估 ruleset 的限制檔案路徑；讀者回饋 workflow 要補強；誤推處置不務實；改回公開時 Actions 紀錄會公開；預覽期 canonical；推送 job 與 PR 觸發的 secret；額度要實測 | 內容完全相同加精確樣式與允許清單；寫死金鑰處理方式；加限制檔案路徑與負向測試；釘 SHA、concurrency、interaction limits；改寫誤推處置；回復前先刪紀錄；加 canonical；獨立 workflow 加受保護的 environment；步驟 2 實測 |
| CI 與專案流程 | 9 | 未登錄期別的快照與 audits 會被整批公開；知識庫違反網站自己的過濾規則；掃描誤判要白名單與測試；讀者回饋程式路徑矛盾；預覽與雜湊互斥；新 job 的條件與釘 SHA；`methods/` 懸空連結；排程 ID 矛盾、交接檔要列為永不公開；claims 欄位揭露 | 快照依已登錄 claims 推導；知識庫套同一過濾規則；fixture 測試；複製到 `tools/`；`SITE_MODE` 與 `PUBLIC_SITE_ORIGIN`；獨立 workflow；連結檢查並納入 publication-check-spec；以 `list_triggers` 實查、交接檔與 audits 列為私人；`verification/README.md` 說明欄位 |

**未採納或部分採納**：

| 建議 | 決定 | 理由 |
|---|---|---|
| S8 轉址改為預設要做（透明度） | 維持預設不做，加 canonical | 改名後誤推到轉址 repo 的風險，需管理者權衡 |
| 連續成功次數降為 3（透明度） | 改為「7 天無失敗且至少 3 天有變更」 | 兼顧 0 則日與觀察期長度 |
| claims 加 `evidence_public` 欄位並由閘門檢查（透明度） | 不改程式；改為「新期別若有無法公開的證據，先建機制再刊出」 | 目前新期別沒有這類證據 |

## 第三輪：Haiku（v0.3 → v0.4）

本輪四個角度皆由 Haiku 執行，各自獨立閱讀 v0.3，共 37 項意見。

**修正者在 GitHub 文件另行核對**：

- 免費方案只能為公開 repo 設定 environment；repo 改私人後，environment 的保護規則與 secret 會被忽略；
- 推送規則（含「限制檔案路徑」）只適用私人與內部 repo。**第二輪寫「免費公開 repo 可用」是錯的**，本輪更正；
- 「個人站台接手已取消發佈的 project 站路徑」查無文件說明，列為實測前提。

**修正者在 repo 另行核對屬實的事項**：

- 知識庫兩條隱藏規則取聯集共 14 筆，`relations.csv` 有 71 列以它們為主體；
- 出版閘門只允許 stylesheet 與 icon 兩種 link；
- `public-site.js` 直接複製已提交的 HTML，不重新渲染；
- `validate-publication.test.js` 第 456 行斷言舊刊連到舊 repo；
- 讀者回饋測試讀取整理程式的位置在第 21–22 行；
- 2026-10-17 是星期六。

| 角度 | 意見數 | 主要發現 | 處理 |
|---|---|---|---|
| 透明度與讀者 | 10 | legacy 例外要寫明；公告「全部留在公開側」不完全屬實；建議轉址；回饋歸檔不放自由文字；預覽橫幅不該說內容相同；`methods/` 要加狀態說明、允許清單要到行；知識庫 README 寫隱藏筆數與圖例；「能核對什麼」改用一般讀者的話；寫明舊 Issue 歸檔方式與統計重新起算；整體再減量 | about 頁照實寫三句；轉址改為預設丙（須實測）；歸檔只留編號、類別、日期、結果；預覽模式整個拿掉；加檔首說明、允許清單以檔案加行內容為單位且 `trig_`／`session_01` 永不放行；README 補齊；改寫第 2 節第 4 點；管理者只需答四項 |
| 執行風險與回復 | 9 | 10/17 是星期六；PR-3 應看 10/29 月報結果；驗收要有每日紀錄，漏記算失敗、不得製造變更、要有放棄期限；回復先關推送開關，步驟 9 是回舊站的最後期限；短訊暫停與補發規則；排程 ID 用 `get_trigger` 確認；每步要有放棄時的清理；PR-C 可早於步驟 1；建議不轉址、拿掉預覽、合併 PR | 改為 10/19 起、最晚 10/23；PR-3 條件式合併；加驗收紀錄與 11/30 期限；改寫回復順序；補發規則；步驟 3 確認 ID；執行表加清理欄；PR-1 可先合併；拿掉預覽、合併為 4 個 PR |
| GitHub 平臺與資安 | 9 | 私人免費 repo 的 environment 不能依賴；檢查與推送同檔，可在分支改掉；限制檔案路徑在公開 repo 無來源；比對基準應是遠端樹；寫死指紋行不通，要完整公鑰行；fork 殘餘風險；`push` 觸發的風險；interaction limits 會擋讀者；報警與提醒沒有機制 | 經文件核對屬實，新增 S9 並照實寫「只防誤觸」；加 main 限定；拿掉路徑限制，私人端檢查為唯一內容防線；改比對遠端樹；改完整公鑰行；步驟 9 前列 fork；不設 interaction limits；寫明失敗通知與每日排程提醒 |
