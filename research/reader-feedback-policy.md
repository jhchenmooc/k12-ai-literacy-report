# 讀者評鑑、公開勘誤與週期改善 SOP v1.1（模擬多專業審查修訂）

建立日：2026/10/08。適用於 K-12 AI 素養國際動態首頁、週報及月報。讀者可透過網站 `/feedback/` 前往 GitHub Issue Form。

## 使用者流程

- 讀者可提供「內容可信度感受」、易讀性 1–5 分或選未評分，並標示問題類型和報告 URL。純評分可以不填段落及長篇說明；具體勘誤請填原始位置、錯誤原因與證據。
- 需具備 GitHub 帳號並登入；內容公開。**沒有提供匿名或機密回饋表單**。請勿公開兒少或其他人的個人資料。
- 每一個成功提交的 Issue 以 `[讀者回饋]` 為標題前綴，作為定期辨識依據。**不依賴尚未建立的 Issue label**。
- 這些評分是志願回覆與方便性樣本，不能解讀為代表全體讀者的科學抽樣，更不能取代事實查核。

## 定期整合與改善

- GitHub Actions 每週一（07:20 UTC，約臺灣 15:20）自動整理最近七個完整 UTC 日的讀者 Issue，統計分類與評分分布；有回饋才開啟一個公開週整理 Issue，避免空週產生無意義議題。
- 週整理 Issue 只收錄類別、有效評分人數（分母）、未評分數、開啟／關閉 Issue 件數及編號連結，不轉貼讀者自填標題與回饋全文；關閉不等於勘誤完成，不將讀者主張直接標示為已核實。
- 編輯檢視每週回饋時，依次優先處理：重大事實／政策效力錯誤、錯誤引述、因果與跨學段誤用、來源連結問題、可讀性和新來源建議。
- **讀者提出錯誤 ≠ 已證實錯誤。** 原始來源核對後才能改報告；需更正時建立分支 PR、通過必要 `verify`、合併並部署。重要錯誤保留透明更正說明與原始 Issue 連結。
- 需資訊不足的回饋標示為待查並在 Issue 說明原因；無法核實或不予採納的建議說明限制，而不是暗中刪除意見。
- 讀者可以在公開 Issues 追蹤處理狀態；若內容涉及個資或惡意張貼，維護者依平台管理與隱私風險進行處置。

## 編輯紀錄建議

每筆更正可記錄：Issue 編號、所涉期別、核對原始來源、風險等級、採納或不採納原因、修訂前後主張、Pull Request、CI 結果及部署後網址。

## 技術／倫理限制

- GitHub Issue Form 的真實提交與管理需要 GitHub 登入，可能降低一般家長／教師的參與率；未設置匿名後端前不可宣稱所有讀者皆可免登入回報。
- 定期彙整的數字是自願回饋量，不推論為報告真實錯誤率或審查正確率。
- 公開週整理只統計有登記 `[讀者回饋]` 前綴的 Issues；若有人手動更改標題或用非模板建立 Issue，可能需要編輯補查。
- 排程整理可能因 GitHub Actions 暫停、權限或服務故障而未執行；可以透過 workflow_dispatch 手動重跑，重複標題會被跳過。
- 靜態首頁無原生存取資料庫，表單採導向 GitHub；沒有在網站上直接儲存個資。

## 模擬多專業審查後的治理補強（2026-10-09）

以下是 AI 依不同專業角色做的模擬審查，不是外聘真人委員會的簽核。

| 專業角度 | 發現風險 | 已調整措施 | 仍存在限制 |
|---|---|---|---|
| 教育測量／統計 | 自願參與的 1–5 分容易誤作可靠度指標 | 更名為「可信度感受」，同列有效評分數與未評分數 | 非隨機自選樣本，不可推估所有讀者意見 |
| 資安／兒少隱私 | 週整理二度引用讀者原始標題可能擴散敏感內容 | 只列 Issue 編號與連結，強化公開警示 | GitHub 原 Issue 仍公開；有人張貼個資需平台管理者處置 |
| UX／無障礙 | 純評分仍強迫填長篇內容 | 段落和說明改成選填；原報告 URL 仍必填以利追蹤 | GitHub 登入門檻仍存在，未提供匿名表單 |
| 教育政策／學術編輯 | 投票不等於已證明政策或論文誤讀 | 每項具體錯誤必核對原始資料，未確認時標示待查 | 無真人專家標準答案；關鍵解讀不得靠評分表決 |
| 軟體工程／維運 | 無評分人數分母、Issue 已關閉容易被誤讀為已修正 | 增列 n 值、未評分與狀態聲明，CI 測試輸出不轉載使用者標題 | 週整理不自動修正內容；排程失敗須由管理者補跑 |

### 精簡工單處理

1. **即時高優先**：明顯個資外洩、錯誤法律效力、重大因果誤導，應盡快人工檢視及必要時發布警示，不能等週報自動整理；公開 Issue 可能需遮蔽/編輯或刪除不當內容（僅管理者操作）。
2. **本週正常處理**：可重現的失效連結、日期、引用段落錯置等，查核後建立 PR 修改；完成時在原 Issue 放 PR 和部署連結。
3. **月度改版排程**：版面、閱讀性、新增欄目需求按回饋頻率與實際研究／政策價值評估，不以票數直接決定證據正確性。
4. **狀態可追溯**：保留「待來源核對／確認問題／修正 PR 中／已部署／不採納附理由」五個編輯處理階段；如無建置 Issue Labels 的管理權限，可先用 Issue 留言與連結記錄，不假稱 Labels 已實裝。
5. **保護報告修訂**：更正須經受保護分支 PR、必須 CI、正式部署；重大勘誤另在報告中刊出修正日期與簡述。

## 免 GitHub 登入渠道（尚未啟用）

已準備 [免登入回饋入口](../feedback/no-login/) 和 [外部收件服務啟用／自檢清單](no-login-feedback-launch-checklist.md)。由於 GitHub Pages 無後端收件，尚未設定 Google Forms 的公開填答網址與隱私說明頁，入口會顯示「尚未開放」，並**不處理或儲存表單資料**。啟用後私有表單回饋不會自動匯入原有 GitHub Issue 每週統計，也不得將私有文字公開轉貼；真正開放須先以未登入的瀏覽器做一筆測試提交並由收件端確認。

## Google Forms 表單連結已提供（2026-10-09，端到端驗收未完成）

使用者已提供 Google Forms 公開填答網址；網站 `feedback/no-login/` 透過 `feedback/no-login-config.js` 連向該表單，並提供 [資料處理與隱私說明](../feedback/privacy/)。

**尚未確認**：未登入 Google／GitHub 時是否能正常進入並送出、Google 表單是否強制收集電子郵件、真正收件端是否收到測試回覆。這些均不可能只靠 GitHub CI 證明。網站狀態保留 `receiptVerified: false`，並明示「待驗收」，不得宣稱已經完成免登入可用性測試。

後續請表單管理者在無痕／登出狀態送出不含真實個資的一筆測試資料，於 Google Forms「回覆」面板確認，再核對不收集電子郵件、無機構限制、不要求登入；只有實際測試成功，才將 `receiptVerified` 改成 true。之後若需每週彙整 Google Forms 的回饋，須另外建立最小權限的聚合管道；**目前 GitHub Issues 每週整理並不統計 Google Forms 回覆**。

## Google 表單暫停（2026-10-09）

依管理者要求，已取消網站對外 Google Forms 的連結及收件配置。`feedback/no-login/` 舊網址顯示暫停說明並導回 GitHub Issues，不收件。既有 Google 表單由 Google 帳戶持有人自行管理；本次不刪除表單或其原始回覆。週報／月報評鑑與每週公開 Issue 彙整維持不變。未來重啟需另行確認需求、隱私與收件測試並透過 PR 啟用。
